# AWS Application Load Balancer: Why can healthy targets still produce HTTP 502?

[Published post in AWS Study Group Vietnam](https://www.facebook.com/groups/awsstudygroupfcj/permalink/2343670456397913/)

:::figure{src="/images/blogs/03-alb-502-keepalive.png" alt="blog-3-diagram" caption="Diagram supplied with the original Vietnamese article"}

An ALB target group can report healthy targets while clients intermittently receive HTTP 502. CPU and memory can look normal, and application logs may show no matching failure. Connection handling and timeout alignment provide another layer to investigate.

### 1. Investigate the connection lifecycle

The article considers an ALB with a 60-second idle timeout and a Node.js service on ECS Fargate with a 5-second keepAliveTimeout.

The ALB reuses backend connections. If the application closes an idle connection earlier than the load balancer expects, a new request can race with connection closure. For example, after roughly six idle seconds, the target may have already closed its connection while the ALB attempts reuse. A FIN/RST and the absence of a usable backend response can result in HTTP 502.

Health checks can still succeed through their own connections. Failures can therefore appear intermittent, particularly around idle periods. A request that does not reach application handling may have no corresponding application log.

### 2. Separate load-balancer errors from target responses

Compare:

- HTTPCode_ELB_502_Count for 502 responses generated by the ALB.
- HTTPCode_Target_5XX_Count for 5xx responses returned by targets.

If load-balancer 502s rise without target 5xx responses, investigate the backend connection path. ALB access logs can help identify entries with elb_status_code = 502 and target_status_code = "-", where no target status was received. Processing-time fields may be -1 when processing cannot be completed or recorded.

Check TargetConnectionErrorCount alongside logs to investigate connection-establishment problems, such as inaccessible targets or security-group restrictions. Aggregate 5xx counts alone do not identify the failing layer.

### 3. Match the fix to the failure mode

**Case 1 — Target keep-alive is shorter than ALB idle timeout**

Check for intermittent 502s with no target response while health checks remain successful. Configure the backend connection timeout to exceed the ALB idle timeout. The article illustrates 65 seconds on the backend for a 60-second ALB timeout.

Examples discussed in the article are Node.js server.keepAliveTimeout = 65000 with a longer headersTimeout, Nginx keepalive_timeout 65s, Gunicorn --keep-alive 65, and Apache KeepAliveTimeout 65. Confirm the behavior of the actual server and version before applying a setting.

**Case 2 — A target stops with requests still running**

Investigate errors aligned with deployment or scale-in. Coordinate deregistration delay with SIGTERM handling so the application stops accepting new work while completing in-flight requests.

**Case 3 — An invalid target response**

For repeatable endpoint-specific errors, inspect HTTP response formatting and oversized headers. The article also mentions invalid payload formatting for Lambda targets as another ALB integration case.

Increasing the ALB idle timeout without reviewing the backend timeout can widen the mismatch. Establish the failure mode before scaling or changing timeout values.

### 4. System design lessons

Review the timeouts across client, load balancer, reverse proxy, and application server together. For this idle-connection issue, the backend needs to keep the connection open longer than the upstream load balancer expects.

Framework defaults should be checked against the actual deployment topology. Separate ALB-generated errors from target responses, correlate them with connection behavior and deployment events, and then validate the proposed fix.
